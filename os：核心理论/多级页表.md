# 第20章 多级页表

> [!INFO] 核心问题
> [[分页机制 (Paging)]]解决了外部碎片，但页表自己可能大到离谱。

---

## 为什么单级页表太大

分页之后，每个进程都有自己的页表。
问题是：页表要给**整个虚拟地址空间**准备映射位置，不管某些虚拟页有没有真的用到。

比如一个进程只用了代码、堆、栈，中间一大片地址空间是空的。
单级页表还是要给这些没用到的虚拟页留表项。

这就很浪费。

---

## 页表大小怎么算

公式很直接：

```text
页表大小 = 虚拟页数量 × 每个页表项大小
虚拟页数量 = 虚拟地址空间大小 / 页大小
```

例子：

```text
32 位地址空间 = 4GB
页大小 = 4KB
虚拟页数量 = 4GB / 4KB = 2^20 个页

如果每个 PTE 4 字节
页表大小 = 2^20 × 4B = 4MB
```

一个进程 4MB 页表看起来还能忍。
但如果有 100 个进程，就是 400MB，而且很多表项根本没用。

---

## 核心思想

多级页表的想法是：
**不要一次性给整个虚拟地址空间分配完整页表，只给真正用到的部分分配页表页。**

也就是把页表本身也分页。

```text
页目录 -> 页表页 -> 物理页帧
```

如果某一大片虚拟地址空间没用到，对应的页表页就不用分配。

---

## PDE 和 PTE

- **PDE（Page Directory Entry）**：页目录项，指向某个页表页。
- **PTE（Page Table Entry）**：页表项，指向真正的物理页帧。

关系大概是：

```text
页目录 PDE
  -> 页表页
      -> PTE
          -> 物理页帧 PFN
```

PDE 更像目录，告诉你去哪个页表页找。
PTE 才是真正保存虚拟页到物理页帧的映射。

---

## 虚拟地址如何拆分

单级页表时：

```text
虚拟地址 = VPN + offset
```

多级页表时，**offset 不变**，只是 VPN 被继续拆开：

```text
虚拟地址 = 页目录索引 + 页表索引 + offset
```

转换流程：

```text
1. 用页目录索引找到 PDE
2. PDE 指向某个页表页
3. 用页表索引在页表页里找到 PTE
4. PTE 给出 PFN
5. 物理地址 = PFN + offset
```

页大小没变，所以页内偏移 offset 不需要重新解释。

---

## 优点

- **节省空间**：没用到的虚拟地址范围，不分配页表页。
- **按需分配**：进程用到哪片虚拟地址，再给哪片分配页表页。
- 页表页本身大小固定，也更容易放进物理内存。

---

## 缺点

- 地址转换次数更多。
  单级页表查一次页表，多级页表可能要先查页目录，再查页表页。
- TLB miss 更贵。
  如果 [[TLB (翻译后备缓冲器)]]没命中，就要真的走多级页表，内存访问次数会增加。

所以多级页表不是免费午餐：
它省了空间，但让没命中时的地址转换更慢。

## 我自己的理解

单级页表像给整栋楼每个房间都准备一张登记表，哪怕很多房间根本没人住。
多级页表像先看楼层目录：这一层没人住，就连这一层的房间表都不用建。

所以多级页表的核心不是让地址转换更快，而是：
**别给没用到的虚拟地址浪费页表空间。**

## 引出下一章

多级页表解决的是“页表自己太大”的问题。
但还有一个更现实的问题：

```text
如果所有进程真正要用的页，加起来超过物理内存怎么办？
```

这就引出 [[超越物理内存：机制]]：把暂时不用的页放到磁盘上。
